# Workshop по событийной архитектуре

Приложение читает почтовое сообщение из указанного почтового яищка. Реагирует на письма, содержащие вложения. Далее оно пытается распознать во вложении товарный чек и распознать цену в нем. Если цена менее 200 рублей, она регистрируется автоматически. Если стоимость товаров и услуг превышает 200 рублей, чек отправляется на бюджетный контроль, где держатель бюджета должен одобрить покупку. В последнем случае стоимость чека также регистрируется в последнем микросервисе.

## Архитектура

Приложение состоит из 8 приложений:

- inbox - чтение почтового ящика
- check-manager - оркестратор распознавания
- tesseract - распознавание средствами Tesseract
- yandex-vision - распознаванияе средствами Yandex Vision OSR
- check-ruler - применение правил для извлечения стоимости товаров и услуг, а так же точки автоматического и ручного котроля (больше или меньше 200 рублей)
- budget-control - система бюджетного контроля для ручного подверждения операции
- check-register - регистрация стоимости товаров и услуг
- event-logger - сбор всех событий системы и их группировка по чекам

В качестве исходного дата-объекта выступает письмо с вложением (товарным чеком), которое читает первый микросервис inbox. Далее вложение проходит через цепочку микросервисов, подвергается распознаванию и в конце-концов регистрируется в микросервисе check-register.

Микросервис event-logger стоит в стороне от конвейера: его очередь `event_logger.in` привязана к обменнику `services` маской маршрутных ключей `#`, поэтому он получает копию каждого сообщения системы. События группируются по `attachment_id` (сквозной идентификатор бизнес-транзакции, ADR-0004), а панель администрирования по адресу http://localhost:8005/admin/ показывает список чеков и хронологию всех событий внутри каждого из них.

## Документация AsyncAPI

Обмен асинхронными сообщениями через RabbitMQ описан спецификацией AsyncAPI в файле `docs/asyncapi.yaml`: каналы, очереди, операции каждого микросервиса и схемы сообщений с примерами.

HTML-документацию по спецификации можно сгенерировать командой (потребуется Node.js):

```bash
npx -y @asyncapi/cli generate fromTemplate docs/asyncapi.yaml @asyncapi/html-template -o docs/asyncapi-html --use-new-generator
```

Готовая документация появится в папке `docs/asyncapi-html` — откройте файл `index.html` в браузере.

Проверить корректность спецификации после изменений можно командой:

```bash
npx -y @asyncapi/cli validate docs/asyncapi.yaml
```

## Наблюдение за системой

Готовые дашборды — в Grafana по адресу http://localhost:3000. Смотреть их можно
без входа; логин `admin` / `admin` нужен только для изменений (которые не
сохранятся — см. ниже).

Адрес открывается сразу на «Обзоре системы»: вверху панель со ссылками на
остальные дашборды, панели администрирования сервисов, RabbitMQ и Prometheus.
Переходить между дашбордами можно и не возвращаясь на главную — в шапке
каждого есть выпадающий список «Дашборды».

| Дашборд | Что показывает |
|---|---|
| Обзор системы | сводка: процессы, очереди, поток сообщений |
| Микросервисы | плашки «работает / не работает» по каждому процессу и его зависимостям |
| Очереди ошибок | сколько сообщений застряло в очередях `<очередь>.error` |
| Очереди детально | глубина, готовность к выдаче, невыданные подтверждения и подписчики по каждой очереди |
| Брокер RabbitMQ | соединения, потоки сообщений, память, аварийные ограничения |

Источник данных и дашборды описаны файлами в `grafana/provisioning/` и
подключаются при старте контейнера. Правки через интерфейс Grafana **не
сохраняются**: дашборды генерируются скриптом из репозитория.

```bash
python3 grafana/build_dashboards.py
```

Grafana перечитает изменённые файлы сама в течение 30 секунд.

Метрики собирает Prometheus — http://localhost:9090. Конфигурация лежит в
`prometheus/prometheus.yml` и монтируется в контейнер; после её правки достаточно
перечитать конфигурацию, не перезапуская контейнер:

```bash
curl -X POST http://localhost:9090/-/reload
```

Собираются данные из двух источников (подробности — в `docs/adr/0010-monitoring.md`).

**Размеры очередей** отдаёт сам брокер: плагин `rabbitmq_prometheus` включён в
RabbitMQ по умолчанию и слушает порт 15692. Разбивка по очередям приходит с
endpoint `/metrics/detailed`, очереди ошибок размечены меткой `dead_letter`:

```promql
rabbitmq_detailed_queue_messages                      # глубина всех очередей
rabbitmq_detailed_queue_messages{dead_letter="true"}  # накопившиеся ошибки
rabbitmq_detailed_queue_consumers == 0                # очередь без потребителя
```

**Работоспособность** сообщает каждый долгоживущий процесс микросервиса —
и панель, и потребитель сообщений, и планировщик заданий inbox. Все они отдают
метрики на порту 9394 и различаются метками `service` и `process`:

```promql
service_up                       # 1 — все зависимости процесса доступны
service_up == 0                  # процессы с недоступной базой или брокером
service_dependency_up            # доступность postgresql и rabbitmq по отдельности
```

Посмотреть метрики отдельного процесса можно и напрямую:

```bash
docker compose exec check-manager-sneakers curl -s http://localhost:9394/metrics
```

## Сохранность состояния

Три сервиса хранят данные на именованных томах: `rabbitmq-data` (очереди,
привязки и накопленные сообщения), `prometheus-data` (история метрик) и
`grafana-data` (внутреннее состояние Grafana). Пересоздание контейнеров эти
данные переживают.

У брокера сохранность работает только вместе с `hostname: rabbitmq` в
`docker-compose.yaml`: каталог данных называется по имени узла
(`rabbit@<hostname>`), а у пересозданного контейнера hostname по умолчанию
новый — брокер поднялся бы с пустым узлом рядом со старым. Менять hostname
у работающего стенда нельзя: очереди останутся в каталоге прежнего узла.

Начать с чистого брокера (очереди пересоздадут сами сервисы при запуске,
кроме `yandex_vision.in` — её объявляет незапущенный сервис):

```bash
docker compose down && docker volume rm event-app_rabbitmq-data
```

## Вспомогательные папки проекта

Некоторые папки не используются непосредственно для запуска приложения:

- docs — файлы и материалы для документирования проекта
- microservice-template — генератор микросвервисов, при помощи которого создавались все микросервисы, за исключением inbox
- tesseract-docker — тестовый проект, для демонстрации распознавание изображений при помощи tesseract (а также инструкция по его установке и использованию)
- yandex-vision-osr - тестовый проект, для демонстрации распознавания изображений при помощи Yandex Vision OSR и (а также инструкция по его использованию)

## Запуск проекта

1. В семи основных проектах необходимо скопировать sample.env в .env и корректно заполнить переменные окружения
2. В корне репозитория следует запустить команду

```bash
docker compose up
```

3. Для каждого проекта, использующего базу данных необходимо выполнить команду для ее создания и развертывания

```bash
docker compose run НАЗВАНИЕ_СЕРВИСА bundle exec rake db:drop db:create db:migrate
```

НАЗВАНИЕ_СЕРВИСА это одно из шести значений: inbox, check-manager, check-ruler, check-register, budget-control, event-logger. Впрочем их можно всегда посмотреть в docker-compose.yaml.

Кроме того, каждый микросервис можно запустить отдельно от остальных, воспользовавашись readme.md файлом в папке микросервиса.

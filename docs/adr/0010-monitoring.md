# 10: Наблюдение за микросервисами и очередями

Дата: 2026-08-03

## Статус

Принят

## Проблема

Prometheus в проекте был поднят, но работал с конфигурацией по умолчанию:
собирал метрики только сам с себя. Состояние системы приходилось выяснять
вручную — панелью RabbitMQ (http://localhost:15672) и `docker compose ps`.

В событийной архитектуре этого мало. Отправитель не знает, дошло ли сообщение
до потребителя, а конвейер молчалив по своей природе: если потребитель упал,
сообщения продолжают копиться в очереди и внешне ничего не происходит.
Особенно это касается очередей ошибок (ADR-0009) — они наполняются молча,
и заметить застрявший чек можно только заглянув в брокер.

Нужны три вещи: признак работоспособности каждого процесса, текущий размер
каждой очереди и отдельно — размер парных очередей `<очередь>.error`.

## Решение

### Размеры очередей берутся у брокера

Опрашивать очереди из приложений не нужно: в RabbitMQ 4.x плагин
`rabbitmq_prometheus` включён по умолчанию и отдаёт метрики на порту 15692.
Данными о своих очередях владеет брокер, он же — единственный источник правды
об их глубине.

Endpoint `/metrics` агрегирует значения по узлу, поэтому разбивка по очередям
собирается отдельным заданием с `/metrics/detailed` и явным перечнем семейств:

| метрика | смысл |
|---|---|
| `rabbitmq_detailed_queue_messages` | глубина очереди |
| `rabbitmq_detailed_queue_messages_ready` | сообщения, готовые к выдаче |
| `rabbitmq_detailed_queue_messages_unacked` | выданы, но не подтверждены |
| `rabbitmq_detailed_queue_consumers` | число подписчиков очереди |

Очереди ошибок — обычные очереди и попадают в тот же список. Чтобы не
перечислять их в каждом запросе, Prometheus размечает их меткой `dead_letter`
по имени (`metric_relabel_configs` в `prometheus/prometheus.yml`):

```promql
rabbitmq_detailed_queue_messages{dead_letter="true"} > 0
```

`rabbitmq_detailed_queue_consumers == 0` на рабочей очереди означает, что
потребитель отвалился, — сбой, который со стороны приложения не виден.

### Работоспособность сервисы сообщают сами

У сервиса два-три долгоживущих процесса на одном образе: панель
(`rails s`), потребитель (`rails sneakers:run`), а у inbox — планировщик
заданий (`bin/jobs`). Работоспособен процесс, а не образ, поэтому метрики
отдаёт каждый из них, на одном и том же порту 9394:

| метрика | смысл |
|---|---|
| `service_up` | 1 — все зависимости процесса доступны |
| `service_dependency_up` | доступность зависимости: `postgresql`, `rabbitmq` |
| `service_start_time_seconds` | Unix-время запуска процесса |

Метки `service` и `process` различают процессы: `service_up{service="check-manager",
process="sneakers"}`. Сам факт ответа Prometheus превращает в метрику `up`,
поэтому приложение публикует то, чего снаружи не видно, — доступность базы
и брокера.

Экспортер (`lib/metrics/`) поднимает собственный TCP-сокет в фоновом потоке,
а не маршрут Rails. Причины: у потребителя и планировщика веб-сервера нет
вовсе, а единый адрес у всех процессов оставляет конфигурацию Prometheus
однообразной. Новых гемов решение не требует — образы пересобирать не нужно.

Короткоживущие процессы (консоль, rake-задачи, спеки) метрики не публикуют:
`Metrics::ProcessInfo.kind` возвращает для них `nil`, и порт не занимается.

### Показывает состояние Grafana

Prometheus умеет строить графики, но держать в голове десяток запросов на
семинаре некому. Дашборды (http://localhost:3000) разложены по вопросам,
которые задают системе:

| Дашборд | Отвечает на вопрос |
|---|---|
| Обзор системы | всё ли в порядке прямо сейчас |
| Микросервисы | какой процесс не работает |
| Очереди ошибок | где застряли сообщения |
| Очереди детально | что происходит с конкретной очередью |
| Брокер RabbitMQ | здоров ли сам брокер |

И источник данных, и дашборды задаются provisioning-файлами из репозитория
(`grafana/provisioning/`), а не настраиваются в интерфейсе: стенд должен
подниматься из чистого состояния одной командой. Правки через интерфейс
Grafana не сохраняются — дашборд меняется в `grafana/dashboards/*.json`,
которые собираются скриптом `grafana/build_dashboards.py`.

## Заключение

Состояние системы собирается в Prometheus (http://localhost:9090) из двух
источников: очереди — от брокера, работоспособность — от самих процессов,
а показывается дашбордами Grafana (http://localhost:3000).
Полезные запросы:

```promql
service_up == 0                                        # сервис с недоступной зависимостью
rabbitmq_detailed_queue_messages{dead_letter="true"}   # застрявшие сообщения
rabbitmq_detailed_queue_consumers{queue="tesseract.in"} == 0  # потребитель отвалился
```

Плата за решение: экспортер входит в каркас микросервиса и, как остальной
общий код, правится в каждом сервисе отдельно и в `microservice-template`.
Правил оповещения (alerting) не заводим — в учебном стенде некому их
доставлять; при появлении Alertmanager запросы выше становятся условиями
правил без изменения метрик.

Метрики самого конвейера (сколько чеков распознано, сколько ушло на ручное
одобрение) сюда не входят — эту хронологию хранит event-logger, у неё другой
потребитель и другой срок жизни.

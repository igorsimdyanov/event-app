# 11: Распределённая трассировка конвейера

Дата: 2026-08-03

## Статус

Принят

## Проблема

Наблюдаемость стенда закрывала два вопроса из трёх. Метрики (ADR-0010)
отвечают, что сломано: процесс не отвечает, очередь растёт, потребитель
отвалился. Журнал event-logger отвечает, что происходило с конкретным
чеком: список событий, сгруппированных по `attachment_id`.

Не закрыт вопрос «сколько это заняло и где». Хронология event-logger
строится по `created_at` с точностью до секунды и знает только момент
отправки сообщения. По ней нельзя отличить сервис, который думал четыре
секунды, от сообщения, которое три из них пролежало в очереди, — а на
семинаре именно этот разрыв объясняет, чем событийная архитектура
отличается от цепочки синхронных вызовов.

Конвейер к тому же ветвится: `recognize` уходит двум распознавателям,
`check-ruler` выбирает между автоматической регистрацией и ручным
одобрением, а копию каждого сообщения получает event-logger. Увидеть эту
структуру целиком — деревом, а не плоским списком — по журналу нельзя.

## Решение

### Коллектором становится Zipkin

Отдельный контейнер `zipkin` (http://localhost:9411) принимает спаны по
HTTP на `/api/v2/spans` и рисует трассу деревом. Хранение — в памяти
процесса: на стенде трассы живут минуты, а внешнее хранилище
(Elasticsearch, Cassandra) стоило бы дороже самого конвейера.

Zipkin выбран за модель данных: спан — это плоский JSON с полями
`traceId`, `id`, `parentId`, `timestamp`, `duration`, — который можно
собрать руками и прочитать глазами.

### Инструментация своя, а не OpenTelemetry

Каркас `lib/tracing/` (около двухсот строк) повторяет решение экспортера
метрик: новых гемов не требуется, образы пересобирать не нужно, а весь
путь спана от создания до отправки виден в репозитории. Автоматическая
инструментация OpenTelemetry дала бы больше данных (SQL-запросы, HTTP,
внутренние вызовы Rails), но принесла бы десяток гемов в каждый из семи
сервисов и спрятала бы за магией ровно то, что нужно показать: как
контекст трассировки переезжает между процессами через брокер.

| файл | роль |
|---|---|
| `lib/tracing/trace_context.rb` | контекст B3: идентификатор трассы и родительский спан |
| `lib/tracing/span.rb` | отрезок работы в формате Zipkin v2 |
| `lib/tracing/null_span.rb` | заглушка для процессов без трассировки |
| `lib/tracing/reporter.rb` | фоновая отправка спанов в коллектор |
| `lib/tracing/consumer.rb` | обёртка приёма сообщения для воркеров Sneakers |
| `lib/tracing/tracer.rb` | фасад `Tracing`: `consumer_span` и `producer_span` |

### Идентификатор трассы — это attachment_id

Отдельный идентификатор трассы не заводится. `attachment_id` (ADR-0004)
уже сквозной для всей бизнес-транзакции, а UUID без дефисов — ровно 32
шестнадцатеричные цифры, то есть готовый 128-битный `traceId` Zipkin.

Выгода прямая: номер вложения из письма, из админки или из журнала
event-logger вставляется в поиск Zipkin и открывает трассу этого чека.
Обратное тоже верно — по трассе всегда видно, о каком чеке речь.

### Контекст едет в заголовках B3

Между сервисами контекст передаётся заголовками AMQP-сообщения по
соглашению B3 (`X-B3-TraceId`, `X-B3-SpanId`, `X-B3-ParentSpanId`,
`X-B3-Sampled`), а не полем в конверте. Причина: формат сообщения
(ADR-0005) — контракт между сервисами, и служебные данные наблюдаемости
ему не принадлежат; спецификация `docs/asyncapi.yaml` от появления
трассировки не меняется.

Плата за это — воркеры перешли с `work` на `work_with_params`: тело
сообщения заголовков не содержит, их приносит третий аргумент.

Сообщение без заголовков (публикация из rake-задачи, ручное возвращение
из очереди ошибок, сервис старой версии) трассу не рвёт: трассировка
берёт идентификатор из `attachment_id` и начинает новое дерево с тем же
номером. Так же — сознательно — устроено ручное одобрение в
budget-control: держатель бюджета нажимает кнопку спустя часы после
приёма чека, отдельной трассой, но с тем же `traceId`.

### Спанов ровно два вида

| спан | когда | что показывает |
|---|---|---|
| `publish <routing_key>` (PRODUCER) | публикация сообщения | сколько заняла отправка |
| `receive <routing_key>` (CONSUMER) | обработка сообщения | сколько сервис держал сообщение |

Имя берётся из маршрутного ключа доставки, а не из поля `routing_key`
конверта: он точнее и различает ответы, отправленные через `reply_to`.
Спан публикации, начатой во время обработки, становится потомком спана
приёма — так в Zipkin появляется дерево конвейера. Разрыв между концом
`publish` и началом `receive` и есть время ожидания в очереди.

Спан помечается тем, по чему его ищут: `action`, `attachment_id`,
`queue`, `process` (`web`, `sneakers`, `jobs`), а при исключении —
`error` с текстом ошибки. Отклонённое сообщение (`reject!`) видно в
трассе красным спаном ещё до того, как оно доедет до очереди ошибок.

### Граф зависимостей считает сам Zipkin

Кроме `localEndpoint` (имя своего сервиса) спан несёт `remoteEndpoint` —
второй конец обмена с именем `rabbitmq`. По этим парам Zipkin собирает
страницу Dependencies: `inbox → rabbitmq → check-manager → rabbitmq →
tesseract` и так далее, а сбоку — `rabbitmq → event-logger`, который
получает копию каждого сообщения. Имя брокера фиксировано константой, а не
берётся из настроек подключения: у всех сервисов узел графа должен
называться одинаково, иначе вместо одного брокера в графе окажется
несколько.

Отдельное Spark-задание `zipkin-dependencies` стенду не нужно: оно читает
спаны из внешнего хранилища (Cassandra, Elasticsearch, MySQL) и туда же
пишет готовые связи, а при хранении в памяти сервер считает их на лету при
каждом запросе. Задание понадобится вместе с переездом на постоянное
хранилище — тогда же появится и смысл в истории трасс глубже нескольких
минут.

### Отправка не мешает конвейеру

Спаны уходят из фонового потока пачками — по сотне или раз в две
секунды. Очередь ограничена двумя тысячами спанов: при недоступном
коллекторе спаны отбрасываются, потому что память конвейера дороже
полноты трасс. Сбой отправки пишется в журнал один раз, а не каждые две
секунды, и на обработку сообщений не влияет — Zipkin в `depends_on`
сервисов не указан намеренно: конвейер работает и без него.

Как и метрики, трассировка не поднимается в короткоживущих процессах
(консоль, rake-задачи, спеки): `Metrics::ProcessInfo.kind` возвращает
для них `nil`.

## Заключение

Zipkin (http://localhost:9411) отвечает на вопрос «где время»: трасса
чека собирается по `attachment_id`, показывает вклад каждого сервиса и
паузы между ними. Три инструмента стенда делят обязанности так:

| инструмент | вопрос |
|---|---|
| Grafana + Prometheus | всё ли работает прямо сейчас |
| event-logger | что происходило с чеком |
| Zipkin | сколько это заняло и на каком переходе встало |

Плата за решение: каркас трассировки, как и экспортер метрик, входит в
общий каркас микросервиса и правится в каждом сервисе отдельно и в
`microservice-template`. Трассы живут в памяти контейнера и пропадают с
его перезапуском. Сэмплирование не настраивается — на стенде поток
сообщений мал, и записывается всё; при росте нагрузки уместно начать
именно с него, флаг `X-B3-Sampled` для этого уже передаётся.

Глубина трассировки ограничена границами сообщений: запросы к Postgres,
S3 и Yandex Vision отдельными спанами не размечаются. Внутреннее время
сервиса видно как длительность спана `receive`, а разбираться, на что
оно ушло, — работа профилировщика, а не трассировки.
